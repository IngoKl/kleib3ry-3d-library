# Reading spike — does a 3D book actually work?

Throwaway spike for the "3D Personal Library" spec. It exists to answer one
question before any architecture gets built:

> Can you read a real PDF, page by page, on a curved 3D page mesh, at 60 fps,
> without leaning into the screen?

**Verdict: yes.** Details and the caveats that change the plan are below.

## Run it

```bash
npm install
npm run assets     # copies pdf.js font data, regenerates public/sample.pdf
npm run dev        # http://localhost:5183
```

`←` / `→` turn pages, `d` re-docks the camera, drag to orbit, scroll to zoom.
Drag any PDF onto the window to read your own instead of the sample.

The sample is generated by [scripts/make-sample-pdf.mjs](scripts/make-sample-pdf.mjs)
and is deliberately hostile: dense 9.5pt body copy, a 6→12pt size ladder, and
0.25pt hairline rules to expose aliasing.

## What was measured

Windows 11, Chrome, 1600×1000 css viewport at DPR 1.5, integrated GPU,
`supersample 2×`, max anisotropy 16×.

| | |
|---|---|
| Page height on screen, docked | **1431 device px** (954 css) |
| Page texture height | 2560 px (≈233 DPI for US Letter) |
| Texel ratio | 1.8–2.1× |
| Steady-state frame rate | **60 fps** |
| 10 s of continuous page turning | **avg 59.8 fps, min 56.3** |
| Frame-rate floor while rasterising a new page | **~40 fps** |
| Texture memory, one spread | ~104 MB |
| Texture memory walking all 16 pages (400 MB budget, LRU) | 388 MB, stable |

At that page size, 9.5pt body copy lands at roughly 26 device px per line. It
reads comfortably; the 7pt row of the ladder is still legible and 6pt is at the
edge. Turning anisotropy off visibly muddies the far half of a page viewed at
37° obliquity and costs nothing to leave on — the spec's claim holds.

## Three findings that change the plan

**1. Legibility is capped by screen pixels, not texture DPI.** A real book page
at a real reading distance is ~500 device px tall, which is illegible no matter
how sharp the texture. The only reason this spike works is that read mode docks
the camera so the open spread *fills the viewport*. So read mode has to be a
camera dock, not "hold the book up while you walk around" — that affordance will
never be readable and shouldn't be promised. Worth writing into the spec.

**2. A 150 DPI page cache is a preview tier, not a reading tier.** Filling a
1000px-tall viewport needs ~2560 px of page height, which is ~233 DPI for US
Letter — and that is at 1.5 DPR on a modest window. Keep the spec's Rust cache,
but treat 150 DPI as covers/thumbnails/peek and budget ~250–300 DPI for the page
actually being read.

**3. Rasterising on the main thread is the only thing that breaks 60 fps.**
Every measured drop below 60 traces to pdf.js rendering a fresh 2560 px page
inline, not to the mesh, the skinning, or the shadows. This is direct evidence
for the spec's Rust pre-rasterisation sidecar: the rendering half of the problem
has headroom to spare, the decoding half does not.

## Three bugs worth remembering

These cost real time here and will recur in the production implementation.

- **Gutter curl must decay to zero.** A constant per-bone rotation keeps
  accumulating along the sheet, so the page dives straight through the page
  block behind it and the outer 85% of the text disappears. Shape the
  *cumulative* angle as `amount · exp(-i/falloff)` and give the bones the
  differences — see [`applyGutterCurl`](src/pageMesh.ts).
- **Rotation sign.** A positive rotation about +Y swings +X toward −Z, i.e. the
  leaf sweeps down through the desk instead of lifting toward the reader. The
  turn base angle has to be negative.
- **LOD target must be reactive.** Holding the required texture resolution in a
  ref means the loader never re-fires when it changes, so quality changes
  silently no-op. It has to be state.

## Not covered

- Only tested against the synthetic sample and whatever you drag in. No scanned
  PDFs, CJK, or embedded-subset font torture tests yet.
- No EPUB. The spec is right that this is the softer problem.
- The camera dock reads the tilt from the previous render, so calling `dock()`
  in the same tick as a tilt change uses the stale angle. Harmless via the UI
  (separate clicks); a nuisance when scripting.

## Driving it from a script

`window.__spike` is the verification surface used to produce the numbers above:

```js
__spike.metrics()          // fps, page px on screen, texel ratio, memory
__spike.set({ supersample: 3, anisotropy: false, tiltRad: 0.9 })
__spike.turn(1)            // 1 forward, -1 back
__spike.pose(1, 0.45)      // freeze a turn mid-flight; pose(1, null) clears
__spike.dock()
await __spike.stress(10)   // turn continuously, report { avg, min, frames }
```
